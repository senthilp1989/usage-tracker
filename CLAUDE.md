# TestEase Usage Tracker

Standalone usage-analytics service for Test Ease. Test Ease POSTs **raw, ungrouped event rows** — one per test case creation, one per test case execution (with its terminal-or-not `status`), one per generated document, one per generated test-case document — to `POST /events` on a fixed interval, batched since its own last checkpoint. No aggregation happens on ingestion: every row is a plain insert into one of four event tables, and the dashboard computes totals and interface breakdowns by grouping those tables at query time. A custom React dashboard (which replaced an earlier Grafana setup) reads these aggregates through the API.

An earlier design (`usage_reports`, one row per user/environment/day, upserted with running totals) has been **removed entirely** — migration `0009` drops the table, and its model, Pydantic schemas and `GET`/`POST /reports` routes are gone with it. It had been frozen (present but unread/unwritten) since raw-event ingestion arrived; the dashboard was already 100% backed by the raw event tables, so nothing changed behaviourally. Historical rows are not recoverable from this repo.

## Tech stack

- **Backend** (`app/`): Python 3.11, FastAPI + Uvicorn, SQLAlchemy 2, Pydantic v2 (+ pydantic-settings, email-validator). Two auth schemes in `app/auth.py`: shared `X-API-Key` header for ingestion, and HMAC-signed 12h Bearer session tokens for dashboard endpoints (login with `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD`; signing key is SHA-256 of `api_key:dashboard_password`, so rotating either invalidates all sessions). Stdlib crypto only — no JWT library.
- **Customer registry** (`app/routers/customers.py`, `frontend/src/customers.ts`): three configuration tables — `customers` (slug id, name, `is_internal`), `customer_rules` (ordered regex patterns, first match wins) and `environment_mappings` (manual overrides, keyed on the normalised name; `customer_id` nullable = pinned Unassigned) — added by migration `0010`, which also seeds Heineken/Celanese/BAT/Tarento-internal and their patterns (id-keyed and additive, so it never overwrites a hand-edited rule). Exposed as `GET`/`PUT /customers/registry` under the same Bearer session; the only UI onto it is the drawer's admin **Customer mapping** tab (a read-only "Customer × stage / Environment registry" section existed briefly and was removed on request — `stageOf` survives only as that tab's Stage column, and `STAGE_ORDER`/`suggestCustomer` went with it). **The backend is the store, not the resolver**: normalisation, pattern matching, override precedence and stage parsing all live in `frontend/src/customers.ts`. That is deliberate — every customer-keyed panel is the matching environment-keyed rollup folded one level further, so customer and environment totals are the same rows by construction, and the admin mapping tab regroups the live page before anything is saved. Patterns use `(?=_|$)`, never `\b` (`_` is a word character, so `^hei\b` misses `hei_test`; the lookahead is also what keeps `^hei(neken)?(?=_|$)` off `heidelberg_dev`).
- **Database**: PostgreSQL 15. Four raw event tables (`models.py`): `test_case_created_events` (+ `test_case_name`), `test_case_executed_events` (+ `test_case_name`, `status`), `document_generated_events`, `test_case_document_generated_events` (+ `suite_name`, `test_case_names`, `test_case_count`; nullable `environment`/`interface_name`) — each with `user_email, environment, interface_name, created_at, reported_at`, unique on those (plus `test_case_name` where present) as a de-dupe backstop, **not** the primary correctness mechanism (Test Ease's own checkpoint is). There is **no `package_name` column** — package association is never populated by the source system (only exists via a live SAP API call the source tool deliberately doesn't make), so rather than store an always-`'unknown-package'` field, it was dropped entirely; see git history if you're tempted to re-add it, there's a real reason it's gone. `created_at`/`reported_at` are **naive datetimes already shifted to IST** — Test Ease converts once before sending (fixed +5:30, no DST), and the DB server default for `reported_at` uses `now() AT TIME ZONE 'Asia/Kolkata'` for the same reason: no timezone math anywhere downstream, which matters once these tables have many rows. These four tables are the whole *event* schema — the old `usage_reports` table is dropped (migration `0009`) — and the only other tables are the three registry ones above, which hold configuration, not measurements. Schema is managed by **Alembic** (`alembic/`); the API container runs `alembic upgrade head` on startup (Dockerfile) — `main.py` no longer calls `create_all()`.
- **Frontend** (`frontend/`): React 18 + TypeScript + Vite, react/react-dom are the only runtime deps — all charts are hand-rolled SVG (`ActivityChart.tsx` stacked columns, `Sparkline.tsx`, `RankedBars.tsx`/`Heatmap.tsx` in plain DOM), per dataviz skill specs: validated palette, chart/table toggle, direct labels. Laid out **aggregate first, detail on demand** per the redesign spec (hero/KPIs → activity → leaderboards → coverage → tabbed detail drawer), with one sticky filter bar scoping everything below it. Light/dark theme defaults to OS preference but is user-toggleable (`theme.ts` sets `data-theme` + persists to localStorage). Served by nginx, which proxies `/api/*` → `api:8000` with the prefix stripped; Vite dev server proxies the same way.
- **Infra**: Docker Compose — `database` (internal-only), `api` (`${API_PUBLISH_PORT:-8000}`), `frontend` (`${FRONTEND_PUBLISH_PORT:-3005}`). All config via `.env` (see `.env.example`); compose fails fast if `API_KEY` or `DASHBOARD_PASSWORD` is unset.

## Running / verifying

`docker compose up --build` with `.env`. Dashboard at :3005, OpenAPI docs at :8000/docs. Local dev: uvicorn + `docker compose up -d database` (see README), `cd frontend && npm run dev`. Frontend check: `npm run build` (tsc + vite). **No automated tests anywhere, no CI** — verify manually via curl (`POST /events` with X-API-Key; `/dashboard/login` → Bearer → `/dashboard/summary?from=...&to=...`, `/customers/registry`).

## Conventions & gotchas

- **Ingestion is append-only, not upsert.** Each row is a plain insert; `ON CONFLICT DO NOTHING` on the natural key (`user_email, environment, interface_name[, test_case_name], created_at`) only guards against Test Ease resending a window it already sent (e.g. after losing its checkpoint state file) — it is not how normal dedup happens. Normal dedup is Test Ease never re-querying past its own checkpoint.
- **`routers/events.py` validates each row individually, not the batch as a whole.** `payload: Dict[str, Any]` (not a typed `UsageEventsIn` body) is validated item-by-item via `schema.model_validate(item)` in a try/except; a bad row is skipped and reported in the response's `rejected` list (`event_type`, `index`, `reason`), everything else still inserts. This exists because checkpoints only advance on a successful send — an all-or-nothing 422 on one bad row would've permanently blocked every retry. Confirmed in practice: `EmailStr` rejects `.local`-TLD addresses (email-validator treats them as reserved/special-use), and the local `DISABLE_AUTH=true` dev bypass in the source tool attributes every row to a mock user — that combination is exactly what surfaced this.
- **`user_email` on the event schemas stays `EmailStr`** — deliberately kept strict rather than loosened to `str`, since per-row rejection above already contains the blast radius of a bad value to that one row.
- **All four event tables use IST-naive timestamps, always.** Never add a `field_serializer`/`.astimezone()` call for `created_at` or `reported_at` on the new schemas — that per-row conversion at read time is exactly what storing pre-shifted IST was meant to eliminate at scale. (The last `astimezone(IST)` serializer went out with `UsageReportOut` when `usage_reports` was dropped — there is no tz-aware column left in the schema, so don't reintroduce the pattern.)
- **`dashboard.py` queries the four event tables and merges in Python.** `_scoped()` does all filtering (date range as a half-open timestamp bound — not `func.date(col) BETWEEN`, so the plain index on `created_at` stays usable — plus user/environment, and on `/artifacts`, interface) as SQL `WHERE` clauses. The per-day (`/daily`) and per-user (`/users`) dict-merging that follows is just reshaping three already-filtered, already-aggregated result sets into one row per key — there is no additional filtering logic client-side or in that merge step.
- `status` is still collected on `test_case_executed_events` (ingestion payload and DB column untouched), but the dashboard no longer surfaces pass/fail counts, a pass-rate KPI, or the per-row `status` column anywhere — `/dashboard/summary|daily|users` only return a plain `test_cases_executed` count now (no `FILTER (WHERE status = ...)`), and `/dashboard/executed-events` omits `status` from the response. If pass/fail reporting comes back, it needs to be re-added to `schemas.py`/`routers/dashboard.py`/`Dashboard.tsx`/`DetailDrawer.tsx` — none of that plumbing exists anymore.
- **The panel grouping moved server-side (the `/rollup` twins).** The by-user and by-environment ranked bars come from `/dashboard/rollup/users` and `/dashboard/rollup/environments`, the heatmap from `/dashboard/user-environment-rollup` (previously written-but-unwired, now live), and the hero's active-days/environment facts from `active_days`/`environments_active` on `/dashboard/summary`. Every one of those is a second GROUP BY over the same combined `(user, environment, day)` subquery `/users/export` is built on (`_users_grouped_query`), which preserves the redesign-spec §8.5 guarantee — panels can't disagree because they summarize identical filtered rows. Keep it that way: never give a rollup its own filter logic. The rollups carry the four metrics as separate columns on purpose — the legend toggles re-total client-side, so a pre-summed `total` column would turn every toggle into a refetch.
- **`/dashboard/users/export` (the flat fact table) is now fetch-on-demand only.** Two callers remain: the filter bar's CSV button and the drawer's "Usage by user" tab (lazy, count via the paginated `/users` twin at `page_size=1`). Nothing fetches it on page load anymore — page-load payload is O(users + environments + pairs), not O(users × environments × days).
- **The standalone environment fuzzy-search box is gone.** The redesign spec puts filters in exactly one row with no per-card filters, so environment search folded into a type-to-filter box _inside_ the environments popover ("Select all" then applies to whatever is visible). The backend `search` query param is untouched and still supported on every scoped endpoint — the UI just no longer sends it, and `api.ts` still threads it as an optional argument.
- **Drawer tabs are server-mode: filter/sort/paginate happen in SQL.** The five heavy tabs (the flat usage-by-user table + four raw event tables) fetch one page at a time from the paginated endpoints, passing `q` (free-text, ORed `ILIKE` across that tab's text columns — tc-doc includes the JSONB name list via a text cast — ANDed on top of the date/user/environment scope), `sort_by` (whitelisted per endpoint; the JSONB column is not sortable and its header is disabled) and `sort_dir`. `total` honors `q`, so the record count and pager reflect the filtered set. The tab CSV and the filter bar's CSV hit the `/export` twins with `format=csv` — a streamed `text/csv` of the **full** filtered-and-sorted set, so "CSV of what the table shows" survives pagination; the JSON `/export` default is unchanged. The two rollup-fed tabs (user totals, usage by interface) stay client-side — bounded by user/interface cardinality and already in memory. Tab-label counts still come from the paginated endpoint at `page_size=1`. The drawer search box is debounced (300ms); one behavioral delta from the old client filter: `q` matches text columns only, not formatted dates/numbers.
- **Legend toggles scope the whole page, not just the chart.** Turning a metric off in the activity chart's legend also drops it from the ranked bars, the heatmap totals and the tooltips — `series` lives in `Dashboard.tsx` and is passed down. Colour follows the metric's fixed slot (`METRICS[i].colorVar` in `types.ts`), never its rank, so filtering never repaints the survivors.
- `/dashboard/artifacts` is the interface breakdown (`test_cases_created`/`test_cases_executed` only — no documents, no pass/fail, no package dimension) sourced from `test_case_created_events` + `test_case_executed_events`, filterable by `interface_name` in addition to the usual date/user/environment. `/dashboard/interfaces` is a distinct-value list for the frontend dropdown, same pattern as `/dashboard/user-emails`/`/dashboard/environments` (all three now `UNION` across the relevant event tables, since there's no single source table anymore). There is no `/dashboard/packages` — see the package-removal note above.
- `/dashboard/users` returns one row per (user_email, environment, report_date) — a rollup of the four event tables' matching rows for that key, not a per-report listing anymore (there's no single "report" row to list). `last_event_at` is `MAX(reported_at)` across whichever of those tables contributed to that key.
- Chart colors are the dataviz reference palette (CSS custom properties in `frontend/src/styles.css`); slot 1 (`--s1`, test cases created) is 2.82:1 on white — below 3:1 by design, so the relief is **mandatory, not optional**: the activity chart must keep both its visible direct labels and its table view, and the heatmap must keep the number in every cell. Don't remove either.
- **The customer axis never gets its own aggregate endpoint.** `Group by: Customer` folds the *existing* environment-keyed rollups (`/rollup/environments`, `/user-environment-rollup`, `/artifacts/export`) through the registry in JS. Adding a `/rollup/customers` would reintroduce exactly the drift the §8.5 single-fact-table guarantee exists to prevent — resist it.
- **Group by defaults to `Environment`, not `Customer`.** The redesign mock defaults to Customer; this app does not, so the page on load is byte-identical to what it showed before the customer axis existed. Reset returns it to Environment (`DEFAULT_GROUP_BY` in `FilterBar.tsx`), and `offDefault` counts it, so the Reset button appears when only the grouping is off-default.
- **A duplicate customer name is refused in both places, on purpose.** `customers.name` is UNIQUE *and* the page groups on the name, so a second "Heineken" would merge two rollups into one bar before the save even failed. The admin screen refuses it with a reason; `PUT` answers 409 (not a 500 from the IntegrityError) and `api.ts` surfaces a 409's `detail` verbatim via `ConflictError`. Override keys are re-normalised server-side too — a raw `Tarento_Dev` key would sit in the table looking live while the resolver, which looks up `tarento_dev`, never matched it.
- **Picking a customer that matches the rule clears the override rather than storing it.** `environment_mappings` is meant to read as "the rules got these wrong"; a redundant row pointing at the rule's own answer makes it unreadable. `PUT /customers/registry` replaces the override set wholesale for the same reason — per-row reset and "Revert all" are *absences*, which a merge can't express. The PUT never renames or re-patterns an existing customer id: seeded rules are shipped configuration, and a dashboard form shouldn't rewrite them by accident.
- **A NULL `environment` 500s six dashboard endpoints — latent, not currently reachable.** `test_case_document_generated_events.environment`/`interface_name` are nullable *by design* (see the model docstring), and `TestCaseDocumentEventDetail` types them `Optional[str]` — but `UserStats`, `EnvironmentRollupStats`, `UserEnvironmentStats`, `ArtifactStats` and `GET /dashboard/environments` all type them plain `str`, so one NULL row makes `/users/export`, `/rollup/environments`, `/user-environment-rollup`, `/artifacts`, `/artifacts/export` and `/dashboard/environments` return 500 and the dashboard fails to load. Verified by hand-inserting one row. It is unreachable today only because `TestCaseDocumentGeneratedEventIn.environment` is a required `str`, so `POST /events` rejects both a missing and a null value per-row — the ingestion schema is stricter than the column. Relax that schema to match the documented intent, or backfill/insert directly, and the dashboard breaks. Fixing it means `Optional[str]` on those four schemas plus null handling in `Heatmap`/`RankedBars`/`customers.ts`; not done, because it changes existing response types.
- **You can add a customer but never remove one.** `PUT /customers/registry` creates manual-only customers and replaces the override set, but there is no delete — for either the API or the mapping tab. A customer added by mistake stays in every row's dropdown until someone runs SQL. `GET /customers` exists and has no caller.
- A Prettier-style formatter hook runs on file writes in this repo.
- Internal-tool security posture: CORS wide open, single shared ingestion key, no rate limiting, no per-user dashboard identity (token payload is just an expiry timestamp).
- Schema changes go through Alembic now: edit `models.py`, then add a revision under `alembic/versions/` (hand-written or `alembic revision --autogenerate`, review either way). A database that predates Alembic (schema built via the old `create_all()`) must be `alembic stamp`ed at the matching baseline revision before `upgrade head` — otherwise it'll try to `CREATE TABLE` on a table that already exists.

## Docs & comments worth knowing

- `README.md` is current and thorough (architecture diagram, config table, curl examples, dev instructions) — keep it in sync with API changes.
- `models.py` docstrings explain the append-only/de-dupe semantics of the event tables.
- History: the service originally ingested per-action events via `POST /events` into a `usage_events` table; that was removed (commit `6cdea00`) in favor of the pre-aggregated `/reports` daily-totals design — which has now itself been superseded by a return to raw per-event ingestion (this time as three typed tables, not one generic `usage_events`). `/reports` was kept frozen-but-queryable for a while as a historical archive, then deleted outright in migration `0009` once it was clear nothing consumed it.
- Migration `0005` dropped `package_name` from all three event tables and added `test_case_name` to the two test-case tables, changing the unique-constraint natural key on all three — written against empty tables (all data had just been truncated for testing when this shipped), so it doesn't attempt to backfill/migrate any pre-existing `package_name` values.

## Open questions / unclear areas

- **Stray `path/to/venv/` directory** at the repo root (a Python 3.14 venv, likely from copy-pasting `python -m venv path/to/venv`). Untracked and not gitignored — probably safe to delete, but confirm.
- Python version drift: Docker uses 3.11, local `.venv` is 3.10, the stray venv is 3.14; `requirements.txt` is fully unpinned.
- The `/export` twins still return all rows unpaginated (JSON or `format=csv`) — but nothing fetches them automatically anymore: JSON exports have no frontend caller left, and the CSV form only runs on an explicit download click, streamed rather than materialized. Unbounded by design for exports; everything page-load or interaction-driven is paginated.
- A still-`RUNNING`/`QUEUED` execution older than Test Ease's 30-minute settle window gets reported with that non-terminal status and is never corrected later — ingestion is insert-only, not upsert. Accepted tradeoff, not a bug.
